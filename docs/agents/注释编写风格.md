# 注释编写风格

注释应当像熟悉业务的开发者带后来者读代码：用专业但自然、记叙性的语言，讲清业务背景、设计原因和数据含义。

## 写什么

- 优先解释代码本身无法表达的信息：业务约束、数据来源、历史原因、模型与现实场景的对应关系。
- 用具体场景解释抽象设计，用输入和输出示例解释数据处理，用实际界面或存储内容解释字段用途。
- 必要时说明流程顺序及步骤之间的联系，尤其是后一步为什么依赖前一步。
- 简短的方法说明可以帮助调用者了解用途；无须把方法体里的操作、分支和返回值逐项复述。
- 注释不只解释“为什么”，也补充类型和命名没有表达的数据约定、业务含义。简短的中文释义只要有助于阅读，就值得保留，不必每条都揭示设计原因。
- 按信息价值决定篇幅。显而易见的代码可以没有注释，复杂的业务背景可以多写几行。

## 不知道“为什么”时

**AI模型不知道设计原因时，应当提问用户，确认后再写。**

现有实现能证明“代码现在做了什么”，不能自动证明“作者为什么这样设计”。不得把推测出的动机写成事实，也不要用“为了提高性能”“保证一致性”“避免潜在问题”等套话填补未知信息。

问题应当具体指出需要确认的设计选择。例如：

> 这里按周次合并记录，周次相同时会保留最后一条。这是教务数据的去重规则，还是沿用旧实现的处理方式？我需要确认原因，才能解释为什么这样合并。

## 怎么写

注释一般不需要说 what 和 when，更需要的是说 why。

- 使用中文陈述句或简短片语，描述事实和因果，不用祈使句指挥读者。
- 语言专业但自然，可以说“我们”“教务系统发下来”“本地存一份”。记叙性意味着把事情讲明白，而不是堆砌“首先、然后、最后”。
- 正面描述实际行为，**去掉无关的“不做什么”“而非什么”等辩解尾巴**。确实影响业务理解的限制和区别仍需说明。
- 专业性来自概念准确，不来自书面词汇的堆砌。自然、准确的口语无须写成抽象的正式表述。
- 流程背景放在流程入口，局部规则放在对应语句旁，字段或分支的简短说明可以放在行尾。
- 普通局部说明采用`//`；类或方法需要文档说明时可以使用KDoc。不要为形式统一，把所有注释都改成块注释或行尾注释。
- 注释范围与代码范围对应，避免一大段注释同时解释后面多个分散的操作。

## 数据模型注释：举一些正例

以 CourseModels.kt 为例。

### 1、类注释先建立概念，再用场景落地

读者首先需要知道类是什么，以及一个实例代表多大粒度的业务对象。容易混淆时，再解释这个粒度意味着什么，并用具体场景指出受影响的字段。如：

```kotlin
/**
 * 本地存储的课程数据模型
 * 按“课程安排”为单位存储
 * 同一门课程的不同安排会生成不同的Course实例
 * 如某门课在周二和周四都有课，则会生成两条不同Course，dayOfWeek、section、key不同
 */
```

这里依次回答“是什么”“按什么单位存”“这意味着什么”“实际例子是什么”。不要只写“负责课程数据建模”，也不要为了简短删掉帮助读者理解粒度的例子。

### 2、把来源、用途、存储方式和设计原因连起来

```kotlin
/**
 * 从Course渲染而来的结果，持久化储存，用于UI直接展示
 * 按“天”为单位存储，一天有多条课程数据
 * 日期是repo的key，RenderedCourse是value，所以不用再存储日期字段
 */
```

这段按读者的疑问展开：从哪里来、给谁使用、怎样存储、为什么没有日期字段。最后一句有明确前因，解释了容易令人困惑的结构选择；“不用再存储”不是多余的否定尾巴，应当保留。

### 3、字段注释交代类型无法表达的约定

```kotlin
val weeks: Int,        // bitmap，第0位对应第1周以此类推，生成方式参见CourseImportParser.kt:parseWeeks
val dayOfWeek: Int,    // 0-6，周日为0
val startSection: Int, // 开始节次，1-12
val endSection: Int,   // 结束节次。start=1 end=2表示第1-2节
val key: String, // 用于摸到对应的Course
```

字段名和`Int`无法告诉读者编码方式、起始下标、取值范围和区间含义。此类约定应当直接说明；区间是否包含端点等容易误解的地方，可以用一个小例子讲清。

## 业务代码注释：举一些对比正反例

### 1、讲数据来源和设计背景，而不是只讲实现

反例：

```kotlin
// 分类映射随本次解析器实例加载，课程和考试共用同一份Trie，不放入全局缓存。
```

正例：

```kotlin
// genre map采用字典树，存储课程编号到课群（课程分类）的映射
// 新教务不再提供查询课群的接口，因此我们暂时本地存一份
// 数据来自旧树维教务（eams）
```

前者描述对象何时加载（从构造方法已经能看出）、被什么用（作为类的成员显而易见）和防御性尾巴，后者解释这份本地数据为什么存在、从哪里来。

### 2. 用真实场景解释模型

反例：

```kotlin
// 一条课程详情可以包含多条安排，先提取公共信息，再逐条生成Course。
```

正例：

```kotlin
// NEUPass把同一门课程的不同排课视为不同的Course对象
// 如：某一门课程可能在周二上午和周四下午都有排课
// 我们就分别存两个Course
```

重点是解释“一门课程”和“一个Course对象”的区别，而不是复述遍历和转换。

### 3. 用具体例子解释数据处理

反例：

```kotlin
// 对地点进行规范化处理。
```

正例：

```kotlin
// 有校区名称时，取其后的内容作为地点并移除重复校区名
// 如：浑南校区 一号A103 → 一号A103
```

### 4. 解释字段在业务里是什么

反例：

```kotlin
// 跳过titleDetail的第一项，遍历剩余元素。
```

正例：

```kotlin
// titleDetail是教务系统里的课程tooltip，为多行纯文本
// 首行是标题，其余项是课程排课安排
```

`drop(1)`已经表达了跳过第一项；注释需要解释第一项为什么要跳过。

### 5. 正面说明行为，去掉辩解尾巴

反例：

```kotlin
// 已排课程必须提供起止节次，缺失时终止解析，不构造不完整的课程。
// 按周次位图合并，周次相同时保留最后一条，而非按地点区分。
```

正例：

```kotlin
// 已排课程数据需要完整，字段缺失时终止解析
// 解析好后，按周次位图合并，周次相同时保留最后一条
```

若相邻代码已经足够清楚，整条注释也可以不写。

### 6. 局部说明贴近对应字段

反例：

```kotlin
// 最后写入课程元数据。停课安排保留记录但显示为灰色；
// 实验课直接归入实践类，其余课程按课程代码查询分类。
```

正例：

```kotlin
// 停课安排保留记录但显示为灰色
color = if (location == "停课") 0xFF888888.toInt() else color,
genre = if (isExperiment) CourseGenre.EXPERIMENTAL // UI 展示实验小烧瓶图标
else getCourseGenre(detail.courseCode.orEmpty()), // 课群图标
```

读者可以直接把说明与具体字段、界面表现对应起来。

### 7. 显而易见的操作可以没有注释

反例：

```kotlin
// 按日期排序，日期相同时再按开始时间排序，形成返回的考试列表。
exams.sortedWith(compareBy<Exam> { it.date }.thenBy { it.start })
```

正例：

```kotlin
exams.sortedWith(compareBy<Exam> { it.date }.thenBy { it.start })
```

没有额外业务规则需要解释时，代码本身就是说明。

### 8. 不编造设计动机

反例：

```kotlin
// 为了避免缓存过期导致课程分类错误，每次导入都重新加载映射。
```

如果没有证据证明这是设计原因，即使听起来合理，也不能这样写。

正例是先向用户提问：

> 分类映射每次导入都会重新加载。这里是为了导入结束后释放内存，还是有其他业务原因？

得到确认后，再写实际原因。
